会议里“重复错误去重”的核心，是把「确定错误」和「Retry错误」分开处理，因为两者判断是否重复时，使用的时间粒度不同。

## 1. 确定错误：按“日期”去重

确定错误只比较错误发生的年月日，不比较时、分、秒。

去重判断键可以理解为：

> 制造编号（製造番号）＋错误代码（エラーコード）＋错误发生日期

例如：

| 制造编号 | 错误代码 | 发生时间           | 判断            |
| ---- | ---- | -------------- | ------------- |
| A001 | E100 | 7月10日 09:15:20 | 保留            |
| A001 | E100 | 7月10日 14:30:45 | 与上一条重复，排除     |
| A001 | E100 | 7月11日 09:15:20 | 日期不同，作为新的一次   |
| A001 | E200 | 7月10日 09:15:20 | 错误代码不同，作为新的一次 |
| A002 | E100 | 7月10日 09:15:20 | 制造编号不同，作为新的一次 |

也就是说，同一台设备、同一个错误代码，只要发生在同一天，即使发生时间不同，也只计算一次。

可以写成类似：

```text
制造编号相同
AND 错误代码相同
AND 错误发生日期相同
→ 重复错误，只计1次
```

这里比较的是日期部分，例如：

```text
2026-07-10 09:15:20
2026-07-10 18:40:35
```

虽然具体时间不同，但日期都是 `2026-07-10`，因此确定错误只算一次。

---

## 2. Retry错误：按完整日期时间去重

Retry错误不能只按日期判断，需要比较完整的发生日期时间，精确到秒。

去重判断键可以理解为：

> 制造编号＋错误代码＋完整错误发生时间

例如：

| 制造编号 | 错误代码 | 发生时间           | 判断             |
| ---- | ---- | -------------- | -------------- |
| A001 | E100 | 7月10日 09:15:20 | 保留             |
| A001 | E100 | 7月10日 09:15:20 | 完全相同，属于重复，排除   |
| A001 | E100 | 7月10日 09:15:21 | 相差1秒，作为另一次错误   |
| A001 | E100 | 7月10日 14:30:45 | 时间不同，作为另一次错误   |
| A001 | E200 | 7月10日 09:15:20 | 错误代码不同，作为另一次错误 |

判断方式是：

```text
制造编号相同
AND 错误代码相同
AND 完整发生日期时间相同
→ 重复错误，只计1次
```

因此，Retry错误即使发生在同一天，只要发生时间不同，就应分别计数。

---

## 3. 两者最重要的区别

| 错误类型    | 时间比较粒度 | 同一天不同时刻 | 完全相同时间  |
| ------- | ------ | ------- | ------- |
| 确定错误    | 日期     | 去重，只算一次 | 去重      |
| Retry错误 | 日期＋时分秒 | 分别计数    | 去重，只算一次 |

举一个最直观的例子：

```text
设备：A001
错误代码：E100

第一条：2026-07-10 10:00:00
第二条：2026-07-10 10:00:01
```

如果是确定错误：

> 两条发生在同一天，因此只算1次。

如果是Retry错误：

> 两条相差1秒，因此算2次。

---

## 4. 为什么要采用两套逻辑

会议里讨论到，现有“見える化”系统基本是按日期汇总错误，因此无法充分区分同一天多次发生的Retry。

但是新告警功能需要更加准确地统计Retry次数，所以决定：

* 确定错误继续采用按日期判断；
* Retry错误采用完整时间判断；
* 不要求新告警与现有“見える化”的计算结果完全一致。

因此，如果将来发现：

> 新告警中的Retry次数，比现有可视化画面显示的次数多

不一定是程序错误，很可能是因为两边的去重粒度不同。

---

## 5. 去重与“交付前错误排除”不是同一个处理

会议中还有一条：

> First Connect Time之后14天以内的错误，视为交付前错误，从告警统计中排除。

这属于“统计对象排除”，不是重复数据去重。逻辑上应区分为：

1. 先根据First Connect Time等条件，排除不属于告警对象的错误；
2. 再对剩余错误进行重复判断；
3. 最后计算错误次数和告警结果。

概念流程是：

```text
原始错误数据
→ 排除交付前错误等非统计对象
→ 区分确定错误和Retry错误
→ 确定错误按日期去重
→ Retry错误按完整时间去重
→ 汇总告警次数
```

## 6. 设计书中最好明确写出的内容

建议至少明确以下几点，否则以后测试时容易发生认知偏差：

* 确定错误的去重键具体包含哪些字段；
* Retry错误的去重键具体包含哪些字段；
* 时间是否确实精确到秒；
* 时间值为NULL时如何处理；
* 去重前是否先执行交付前错误排除；
* 新告警与现有“見える化”的件数可能不一致；
* 同一设备、同一错误代码、同一天多次发生时，两类错误的处理方式不同。

目前会议中已经明确的主要字段是“制造编号、错误代码、发生日期／发生日期时间”。如果数据库里还存在错误种类、系统来源、Retry区分标志等字段，是否也要加入去重键，最好在正式表设计中再次确认，不能自行推定。
