### 1. 重新设计“不良率”的数据处理方案

对方认为你目前的设计还缺少一条清楚的处理路径：

> 原始数据 → 中间表／View → 分子与分母 → QuickSight过滤 → 不良率及颜色显示

目前你提出了“新建一张不良率结果表”的方案，但对方暂时无法判断是否合理，因为还没看明白：

* 要建立几张表、View或中间表
* 每张表保存什么数据
* 分子从哪里取得
* 分母在哪里计算
* 不良率是在DB中计算，还是在QuickSight中动态计算
* QuickSight过滤后如何重新计算不良率
* 如何判断某个月发生过错误并显示颜色

所以对方明确要求你：

> 再考虑一下整体采用什么结构；形成方案以后，再向他们共享。

这应该是你当前最主要的任务。

---

### 2. 必须考虑QuickSight过滤器的影响

这是对方这次特别指出、而你之前没有充分考虑的地方。

如果用户在QuickSight中按照以下条件筛选：

* 机种
* Gas Type
* Error Code
* 月份等

那么分子数量会变化，不良率也必须随之变化。

因此，对方认为：

* DB中预先计算并保存固定“不良率”，意义不大；
* DB至少保存分子和分母所需的数据；
* 最终的除法和不良率计算，很可能要放在QuickSight中动态执行；
* 具体如何拆分，仍需要你设计。

也就是说，你不能只做一张固定结果表，然后把已经算好的不良率直接展示出来。必须验证筛选条件改变以后，不良率是否也能正确变化。

---

### 3. 考虑“错误发生月份”的颜色显示

画面要求中存在类似这样的需求：

> 某个月发生了错误，就在QuickSight画面上给该月份标记颜色。

对方指出，目前的数据结构可能无法直接实现这个效果。

你需要考虑：

* DB中是否增加“该月是否发生错误”的Flag
* 是否可以利用现有的 `is_alert` 一类字段
* 还是在QuickSight中通过计算字段判断
* 初次发生和普通发生是否需要区分
* 过滤后颜色显示是否仍然正确

会上你已经回答“先记下来，之后考虑如何处理”，因此这已经属于你的待办事项。

### 4. 累计连接台数必须纳入设计

虽然“累计连接台数”的具体定义还没有最终确定，但对方明确表示：

> 无论最终采用哪一种算法，都必须持有某种形式的累计连接台数，并基于它继续设计。

目前争议有两种算法：

* 每个月都使用当前所有记录的总数，例如每个月都使用46台；
* 按月份累计，例如3月5台、4月累计20台、5月继续累计。

明天由负责人向需求方确认最终采用哪一种。

所以你现在不用自行决定最终算法，但需要提前考虑：无论确认结果是哪一种，你的数据结构都能保存并处理累计连接台数。
