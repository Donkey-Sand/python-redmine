不过，能否完整读取资料，比单纯换模型更关键。 你截图里的工具，即使选了强模型，也要确认它实际读到了：

文件	需要特别确认的内容
TXT／会议记录	是否完整读取，是否区分讨论、提案和最终决定
PDF	扫描件是否识别成功，图表和批注是否遗漏
Excel	是否读取全部相关工作表、公式，而不只是显示值
SQL	是否追踪到引用的表、View、函数及关联条件

模型官方支持的上下文长度，也不等于你使用的软件会把整个目录全部交给它。

对你这种项目，我建议分三轮做：

1. 盘点资料：先生成文件清单、各文件用途、读取结果和未能读取的部分。
2. 还原需求：整理业务目的、数据流、计算规则、需求变更，以及资料之间的冲突。
3. 编写仕様書：形成处理流程、表／View设计、SQL逻辑、边界条件和测试方案，并给每条关键规则标出出处。

你可以直接给它下面这段指令：

请分析当前项目目录中的全部相关资料，包括 TXT、PDF、Excel、SQL 等，最终编写日文开发仕様書。

请分阶段执行，先完成资料盘点与需求分析，再编写仕様書。

1. 列出文件清单，记录每个文件的用途、版本日期、读取状态，以及未能读取的内容。Excel需要检查相关工作表与公式，PDF需要检查图表和扫描页面。
2. 交叉核对会议记录、需求资料和现有SQL，区分「已确认需求」「现有实现」「推测」「待确认事项」。不要把现有代码自动当成正确需求，也不要把会议中的提案当成最终决定。
3. 对关键结论标注来源：文件名、页码、工作表／单元格或SQL位置。资料冲突时列明差异与判断依据。
4. 输出项目概要、业务规则、数据流、处理流程、表／View设计、计算逻辑、异常与边界处理、测试方案，以及待确认问题。
5. 缺少依据的内容明确标为「要確認」，不要自行补成已确定规格。
