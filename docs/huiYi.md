# 四、QuickSight过滤器：规则已经基本明确

会议中的四个筛选条件，根据后续讨论基本可以还原为：

* 机种
* Gas Type／ガス種
* 错误分类（確定／リトライ）
* Error Code

## 1. 机种筛选：分子和分母都要变化

例如：

* 全部设备连接台数：5000
* 筛选PT7以后：4000

那么不良率应使用：

[
PT7的错误件数 \div PT7的连接台数4000
]

机种是业务人员基本一定会使用的筛选条件。

---

## 2. Gas Type筛选：分子和分母都要变化

例如：

* 机种：PT7
* Gas Type：13A

分母应使用“PT7＋13A”对应的连接台数。

如果筛选LP，则使用“PT7＋LP”对应的连接台数。

对方认为Gas Type可以从Master中取得，因此从数据上应该能够实现。但“机种＋Gas Type组合后的正确连接台数”还需要你进一步确认和验证。

---

## 3. 错误分类筛选：只改变分子，不改变分母

错误分类指：

* 確定
* リトライ

会议已基本明确：

> 確定和リトライ应共用同一个分母。

例如PT7＋13A的连接台数是4000：

* 確定不良率＝確定错误件数÷4000
* リトライ不良率＝リトライ错误件数÷4000

不应该因为选择“確定”或“リトライ”而把分母改变。

原因是：

* 分子来自错误数据，能够区分確定／リトライ；
* 分母来自FC List的连接设备数据；
* 连接设备本身不存在“这是確定设备还是リトライ设备”的概念。

因此，分母与错误分类是相互独立的。

---

## 4. Error Code筛选：只改变分子，不改变分母

会议中也表示：

> 错误代码可以共用分母。

原因同样是：

* 连接台数不是按Error Code保存的；
* Error Code只属于错误事件；
* 设备本身没有对应的Error Code属性。

因此选择某个Error Code后：

* 分子变成该Error Code的件数；
* 分母仍然使用筛选后的机种＋Gas Type连接台数。

---

## 最终过滤规则

| 筛选器        | 分子 | 分母 |
| ---------- | -- | -- |
| 月份         | 变化 | 变化 |
| 机种         | 变化 | 变化 |
| Gas Type   | 变化 | 变化 |
| 確定／リトライ    | 变化 | 不变 |
| Error Code | 变化 | 不变 |

这部分是本次会议最重要、也最明确的成果。

# 五、分子和分母需要分开设计

需求方明确表达：

> 分母和分子基本上希望切分开。

原因是两者属于不同的数据世界：

* 分子：发生错误的数据；
* 分母：投放市场／连接到网络中的全部设备；
* 没有发生错误的设备也必须计入分母；
* 分母不能因为错误分类或Error Code筛选而缩小。

因此，不建议简单把分母塞进每条错误记录，然后对它进行SUM。

比较合理的设计方向是：

* 分子数据集：错误件数，支持所有错误维度；
* 分母数据集／View：月份＋机种＋Gas Type对应的连接台数；
* QuickSight根据月份、机种、Gas Type进行关联或计算；
* 確定／リトライ和Error Code只过滤分子。

# 六、不良率计算起点：基本确定

需求方明确表示：

> 各机种从投入市场的时间开始，按月计算不良率。

会议中讨论了从哪个字段取得“上市月份”。

目前找到一个类似Model Information／FC相关表的Release Date字段。不过该字段似乎比实际上市月份早一个月，例如：

* 表中的Release Date：3月
* 实际大约4月上市

因此会议中提出并基本认可：

[
不良率计算起点=Release Date+1个月
]

也就是说：

* [ ] 优先寻找是否存在更直接的“上市开始月”字段；
* [ ] 如果没有，就使用现有Release Date；
* [ ] Release Date加一个月作为开始月份；
* [ ] 从这个月份开始逐月显示不良率。

这一点比累计分母逻辑更接近确定，但最好还是在设计书里写成：

> 如无更直接的上市年月数据，则暂定使用Release Date＋1个月。

# 七、历史不良率是否每天重新计算：尚未确定

会上询问了：

* 过去所有月份是否每天都重新计算；
* 还是历史数据只计算一次，之后每天只计算最近月份。

结论是：取决于最终采用哪种分母逻辑。

## 如果过去月份使用当前总连接台数

设备增加后，过去月份的分母也会改变。

因此：

* 过去月份的不良率也会变化；
* 需要重新计算历史月份；
* 不能只处理最新月份。

## 如果过去月份保存当时的累计台数

历史月份分母固定。

因此：

* 过去月份一般不需要每天重新计算；
* 每天只需处理当前月份或新增数据；
* 处理成本更低。

这项需求与“累计台数采用哪种方式”绑定，目前一起带回确认。

# 八、件数差异：明确了下一步调查方法

你们已经检查约两天的数据，发现：

* 確定：大约九成一致，但不是完全一致；
* リトライ：大部分不一致；
* 你们应用计算出的件数基本都比需求方多；
* 暂时没有发现你们比对方少的情况。

因此怀疑：

* 你们可能多捞取了部分记录；
* 双方过滤条件可能不同；
* リトライ的判断条件可能不一致；
* 去重逻辑可能不同。

会上你们要求需求方提供对应件数的原始数据，需求方回答：

> 出せると思います。
> 应该可以提供。

接下来的处理是：

* [ ] 等需求方提供原始记录；
* [ ] 将对方4件记录与你们6件记录逐条比对；
* [ ] 找出多出的2件；
* [ ] 优先调查リトライ判断条件；
* [ ] 确认確定部分剩余约一成差异；
* [ ] 确认是否有重复、状态判断或时间范围问题。

这里不是要求你现在盲目修改SQL，而是先拿到原始数据再定位差异。

你可以按下面的方式说明：

> 分子はエラー件数を使用し、分母は機種・ガス種・対象月ごとのネットワーク接続台数を使用する想定です。機種およびガス種のフィルターは分子・分母の両方に反映し、エラー分類（確定・リトライ）およびエラーコードのフィルターは分子のみに反映する構成で検討します。
